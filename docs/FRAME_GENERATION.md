# Experimental frame generation

HeavenBench has optional native Vulkan frame-generation integrations. They default off and are development features, separate from the published 1.0.1 packages. FSR 3.1 runs AMD's optical-flow and interpolation shaders; the optional Windows DLSS adapter uses NVIDIA Streamline. Selecting a provider does not guarantee it is available: the diagnostics show the requested mode, effective mode and the reason for an unavailable path.

| Provider | Build target | Current evidence and limits |
| --- | --- | --- |
| FSR 3.1 | Linux and Windows Vulkan, explicit SDK build | Native Linux Radeon interpolation, temporal rasterization, lifecycle and bounded full-scene validation checks pass. Windows, other GPUs, full-scene quality, latency and display cadence remain unqualified. |
| DLSS | Windows Vulkan, explicit Streamline header build and supplied signed runtime | Real bootstrap, native device/presentation hooks, temporal-resource tagging and Reflex integration are implemented. Host contracts pass; native Windows/NVIDIA execution remains untested. |
| Off | All ordinary builds, including OpenGL, macOS and Android | Ordinary rendering remains available without either SDK. Frame generation is unavailable on these other rendering/platform paths. |

Frame generation inserts an intermediate image between rendered source frames. It adds GPU work and history resources, and does not increase simulation or input-update frequency. Rendered FPS, generated images, native presentation submissions and images confirmed on a display are different measurements. HeavenBench does not currently have display feedback that proves scanout.

## Controls and score policy

Use **Settings → Frame generation** or `--frame-generation off|fsr3|dlss`. The saved configuration key is `frame_generation`; presets do not select a provider. DLSS must be selected at startup because Streamline participates in Vulkan device creation. Changing between native presentation providers can require restarting; the capability reason explains when the current device cannot serve the selected mode.

Both providers currently require SDR and fixed rendering resolution. Disable HDR and dynamic resolution before requesting frame generation. DLSS also requires actual IMMEDIATE presentation: FIFO fallback and unknown presentation modes are rejected. FSR can submit through FIFO, but the current Wayland FIFO captures do not establish even spacing or a higher displayed frame rate.

The DLSS path currently refuses incomplete temporal coverage when particles, heat haze, either cloud layer, god rays, volumetric fog, lens flares, refraction or active rain are enabled. This is a reported integration limit; the application does not silently change those settings. Its implemented input path covers opaque/masked geometry, instance transforms, displacement carriers, GPU bones, CPU-deformed positions and grass history. FSR optical flow is available experimentally with the complete scene, while transparent effects, disocclusion and temporal lighting changes still need visual acceptance.

Any benchmark tour that requests frame generation becomes diagnostic and unscored, including unavailable requests and requests later switched off. Its frame statistics and reports remain available. Ordinary scored comparisons require frame generation off, matching application/score versions and effective settings.

## Build FSR 3.1

Install the normal [source-build prerequisites](BUILDING.md), plus `glslangValidator`. Install SPIRV-Tools to validate generated modules with `spirv-val`; the build records whether that optional validator ran. Prepare the checksum-pinned source explicitly, then enable the renderer option in an isolated build tree:

```bash
python3 scripts/fetch_fsr31.py
./scripts/build.sh --build-dir build/renderer-fsr3 \
  --cmake-arg -DHEAVEN_ENABLE_FSR3=ON \
  --cmake-arg "-DHEAVEN_FSR31_SOURCE=$PWD/build/dependencies/fidelityfx-sdk-1.1.4"
./scripts/run.sh --build-dir build/renderer-fsr3 --data assets/assets.zip \
  --frame-generation fsr3 --no-dynamic-resolution
```

Windows uses the same `HEAVEN_ENABLE_FSR3` and absolute `HEAVEN_FSR31_SOURCE` CMake cache options after the normal native MSVC configuration. Install a native Vulkan SDK and `glslangValidator` first. The current source path builds portable compute components and HeavenBench's presentation bridge; it does not use AMD's Windows swapchain replacement. Windows execution has not been accepted.

The pinned source is [FidelityFX SDK 1.1.4 / FSR 3.1.4](https://github.com/GPUOpen-LibrariesAndSDKs/FidelityFX-SDK/releases/tag/v1.1.4), commit `c6efa6bf7f2027b3ec94f28578bb5965eabb9e55`, archive SHA-256 `eff7e8e371b2d461b980f8c75583133f771e940ed7aa00779dbbaf6dd2f88746`. CMake checks the reviewed source files and generates genuine optical-flow/interpolation shaders. Exact, documented transforms address Vulkan core aliases, scratch alignment, Unix context size and the omitted Windows swapchain callback without editing the fetched originals. See the [provider implementation notes](../benchmark/src/rhi/frame_generation/README.md).

The provider checks Vulkan 1.1, storage-image features, supported formats and subgroup operations. Its generated SPIR-V 1.3 shaders target the same Vulkan environment and are validated with `spirv-val` when installed; all 102 modules passed that check in the recorded Linux build. Physical-device support and enabled logical-device features are checked separately. Keep the FidelityFX SDK and SPIRV-Reflect notices with distributions containing this optional code.

## Build DLSS

Prepare the pinned public headers and framework license. The helper downloads the verified official source archive and extracts only these selected inputs; it does not extract runtime DLLs:

```bash
python3 benchmark/src/rhi/frame_generation/dlss_fetch_sdk.py
```

After configuring the normal Windows renderer, add `-DHEAVEN_ENABLE_DLSS=ON` and `-DHEAVEN_STREAMLINE_HEADERS=C:/absolute/path/to/build/dependencies/streamline-2.14.1-headers` to that build's CMake configuration, then rebuild. Configuration verifies the existing manifest without network access. The default option is off. Two adapter translation units use C++20 to avoid a defect in the pinned SDK's C++23 branch; the renderer stays C++23 and the SDK headers stay unchanged.

Supply an absolute `HEAVEN_DLSS_PLUGIN_DIR` containing signed production `sl.interposer.dll`, `sl.common.dll`, `sl.dlss_g.dll`, `sl.reflex.dll`, `sl.pcl.dll` and `nvngx_dlssg.dll`, and set `HEAVEN_DLSS_PROJECT_ID` to the intended NVIDIA project identity. Launch with `--frame-generation dlss`. The loader verifies the interposer's NVIDIA production signature before loading it; Streamline checks its plugins internally. HeavenBench does not bundle or automatically fetch those DLLs. Their distribution is governed separately by the [DLSS SDK license](https://github.com/NVIDIA/DLSS/blob/main/LICENSE.txt).

This adapter pins [Streamline 2.14.1](https://github.com/NVIDIA-RTX/Streamline/releases/tag/v2.14.1), source archive SHA-256 `34d6e8b70a641c734299a6430aa8ef5be7d7ba8de28a47186b5707e439bd645b`. It uses the official Vulkan instance/device creation proxies and mandatory surface/swapchain/acquire/present/device-idle hooks, plus matching Streamline frame tokens and Reflex markers. NVIDIA hardware, driver and Windows prerequisites are queried through the SDK; public Linux DLSS super-resolution support does not establish Linux frame-generation support. See [DLSS integration details](../benchmark/src/rhi/frame_generation/dlss_integration.md) and NVIDIA's [DLSS-G guide](https://github.com/NVIDIA-RTX/Streamline/blob/v2.14.1/docs/ProgrammingGuideDLSS_G.md).

## Temporal resources and lifecycle

An ordinary Off startup creates no frame-generation runtime or temporal GPU passes. After an explicit FSR request is switched back to Off, the retained runtime uses a real-only native presentation callback to preserve exact counters, without temporal draws or SDK work. SDK-off builds use the ordinary Vulkan platform; an optional FSR build creates its presentation platform with the device so generation can be requested later.

An application-owned temporal scene produces full-resolution signed current-to-previous motion and reversed depth. Static geometry shares uploaded buffers; animated transforms, GPU-bone palettes, CPU-deformed positions and grass retain the previous accepted source state. Rejected submissions do not advance that history. First frames, camera cuts, resize, scene reload and long frame gaps invalidate history rather than connecting unrelated frames. The native callback also checks elapsed monotonic wall time because a prepared packet can remain queued across process suspension. Native swapchain recreation and failed submission publish a separate history epoch, which the driver callback checks immediately before SDK recording; a packet queued before an implicit same-size recreation cannot reuse the retired history while the application still awaits its status event.

The SDR output owns a HUDless color target, separate premultiplied UI, depth and motion textures. It detaches borrowed UI targets before resizing or destruction. FSR interpolates the scene and applies the current UI to both presentations. DLSS receives the separate UI tag and unjittered camera constants. Transparency and missing deformation data cannot be inferred from camera motion alone.

Filament queues a bounded native callback after the input draws, outside render passes. The Vulkan driver retains the textures for command completion, exposes their native image/view/allocation/usage and temporarily synchronizes them for compute. Failed native recording is discarded through an isolated secondary command buffer. DLSS tags the restored image layout used later at presentation and separately retains owning textures until presentation drains.

The FSR platform preserves the real native image, presents the generated image first, then acquires another image and restores/presents the real one. It never acquires an additional image while holding the original acquisition. Per-image fences and presentation semaphores bound reuse; resize and teardown drain outstanding native work before releasing resources. Unarmed ordinary presentation retains the base path.

## Counters and captures

The diagnostic sidebar and paired HTML/JSON reports distinguish real rendered frames, rejected real attempts, successfully recorded eligible interpolation work, real/generated native submission counts, failures and display feedback availability. Recording interpolation commands does not establish GPU completion. Unavailable coverage is exported as `null`, not a measured zero. Report counters start when the current renderer's frame-generation runtime is created and reset on renderer reload; native counts become unavailable if any accepted frames escape native tracking. Streamline's separate cumulative SDK count combines real/generated submissions and does not identify a generated-frame split or display scanout.

`HEAVEN_FG_CAPTURE_DIR=/absolute/writable/directory` enables a bounded native validation readback for the first four FSR generated/real pairs. Each pair contains native-format PPM images and a JSON receipt with source ID and CPU monotonic presentation-return/readback-completion times. This diagnostic waits for GPU completion and changes performance; it must be off for performance measurements. Renderer screenshots alone capture the real image and cannot prove generated presentation quality. `HEAVEN_FG_CAPTURE_START_SOURCE=N` delays the first eligible pair to source N (strict decimal 1..1000000, default 1). Invalid values disable diagnostic capture with an explicit reason. `HEAVEN_FG_CAPTURE_UI_INPUTS=1` additionally saves the same generated image immediately before UI compute as PPM and the raw premultiplied RGBA8 UI as PAM. Receipts correlate those inputs with the final native pair; discarded/unarmed inputs cannot be published as a match. The actual staging allocations, including native requirements, are bounded to 128 MiB and retained until draining. Capture allocation, fence or export failures disable the diagnostic rather than the provider.

For reproducible close moving shots, `--capture-camera-to X,Y,Z,YAW,PITCH` interpolates from the required `--camera-pose` across accepted real sources in a fixed-step `--capture`. Positions and pitch interpolate linearly; yaw takes the shortest route. Rejected submissions keep the same pose, generated presentations do not advance it, and the last source includes the `--capture-count` tail. The option rejects real-time capture, an authored tour, invalid endpoints and fewer than two total sources. Capture sidecars snapshot the actual source pose before asynchronous readback completes, recording start/end/current pose, source ordinal, fraction, FOV and clock. It is a transient diagnostic option, not a saved camera animation setting.

The maintained [motion fixture](../tests/visual/frame_generation_motion.json) covers dense authored grass, day/night smoke and close night glass using real images with generation off. Run it through `scripts/visual_audit.py`; custom motion uses the structured `pose_to` field, whose per-source sidecars are checked. The fixture deliberately does not qualify generated pixels: those require the native paired readbacks above and separate review. Host tests cover interpolation, rejected-source identity, CLI constraints and malformed motion receipts.

## Night lighting and SDK view lifetime, October 13

Matched application/native real images ruled out the native copy, while empty UI inputs ruled out UI composition. The pattern persisted with SDK interpolation commands replaced by an explicitly invalid black diagnostic image and with the extraction passes omitted. Even an empty temporal view could trigger it. Removing all extra temporal views hid the symptom, which was an isolation control rather than a retained feature reduction.

Filament's `Froxelizer::prepare` allocated asynchronous light-grid outputs inside a command-stream `NoopCommand`, but shadow/structure rendering could flush and recycle that stream before `commit` queued the payload's upload. The retained fix keeps worker outputs in the render-pass arena through the worker join, then copies each output into fresh command-stream storage immediately before its upload. It adds at most 96 KiB plus alignment to the existing 16 MiB application arena, with no shader, light-count or geometry reduction and no ordinary GPU wait. The same failing full-temporal isolation capture now has smooth lighting, exits zero and reports zero Vulkan validation errors/warnings. With real SDK interpolation restored, three moving full-scene captures each complete 120 real frames and four diagnostic native pairs with zero Vulkan validation errors/warnings and no presentation failures. The night sources 90–93 are clear of the earlier rectangular corruption in both real and generated images. House/airship captures retain coherent broad color and contours, with softer generated fine detail. These sparse images do not establish continuous-video quality or an exact intermediate-time ground truth.
