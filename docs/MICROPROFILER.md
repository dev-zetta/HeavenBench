# Microprofiler

The microprofiler records instrumented application, loading, simulation, Filament and render-pass work for diagnosis. It provides an in-app viewer and self-contained JSON/HTML exports. It does not replace benchmark scores or the existing fixed-camera `--profile` measurement. Focused CPU/widget checks, native Vulkan/OpenGL query/lifecycle checks and a sequential Linux overhead cohort have saved evidence. Each measured checkpoint below is tied to its frozen executable. Native Windows and real browser interaction remain open; bounded Android fixture captures and touch/lifecycle checks have separate device receipts.

## Interactive controls

Open **Diagnostics → Microprofiler** or press **F6**. Opening, closing or freezing the panel does not start or stop recording. The toolbar's **Recording** indicator reopens a closed panel while capture continues. Android uses the same Diagnostics menu without requiring a keyboard.

| Control | Behavior |
| --- | --- |
| Record | Starts a new capture and replaces retained history from the previous capture. |
| Stop | Stops collection while keeping the captured history available. |
| History (s) | Rolling retention requested for the next Record, from 0.1 to 3600 seconds; default 10. This is not an interactive automatic-stop timer. |
| Freeze / Unfreeze view | Keeps an immutable snapshot visible while recording continues, or returns to live snapshots. |
| Save trace | Writes the exact displayed live/frozen snapshot as matching `.json` and `.html` files without stopping recording. |
| Output base | Empty chooses an automatic `capture-<steady-clock-ns>` name under writable user storage's `profiles/` directory. Relative names use that directory; explicit absolute prefixes are supported. |

Record/Stop, Freeze and Save remain first, followed immediately by the frame graph and CPU timeline. Capture options, Help and View controls are collapsed below the timeline; they hold history/output settings, explanations, search/filter controls and fit/follow/pan controls. Errors remain visible and saved-path details remain available under Capture options or the feedback tooltip. The frame graph preserves the longest observed interval in each pixel column; clicking it focuses that interval. Purple incomplete frames are partial observations, not full frame times. The CPU timeline shows nested tasks by thread, with task/category search, thread/category filters, wheel or button zoom, drag/slider pan, selection details and fit/follow controls. The GPU viewer selects a native frame/renderer and shows clickable pass bars on that frame's separate GPU-relative axis, with previous/next/latest controls. Unavailable samples remain selectable rows without fabricated bars. Selecting a CPU attempt can select its correlated GPU frame; Focus linked CPU attempt changes the CPU view through capture/attempt identity only, without aligning clocks. Selecting a pass pins its frame and selection across snapshot refreshes and newer frames while that frame remains retained; Latest resumes automatic following. Selected pass details retain status, source, capability and workload counts. Live snapshots refresh at most four times per second while the panel is open. Freezing changes the displayed snapshot, not collection.

## Command line

These options are transient startup controls and are not written into the saved rendering configuration:

```bash
# Ten-second trace with the profiler panel hidden and application controls retained.
./scripts/run.sh --data assets --microprofile build/traces/ledge \
  --microprofile-seconds 10 --camera-pose '-9.8,24.3,27.5,90,-40'

# Same recording with the profiler panel visible.
./scripts/run.sh --data assets --microprofile build/traces/ledge-visible \
  --microprofile-seconds 10 --microprofile-visible \
  --camera-pose '-9.8,24.3,27.5,90,-40'
```

`--microprofile BASE` requires a nonempty output prefix. `--microprofile-seconds N` accepts a finite value from 0.1 to 3600, defaults to 10 and requires `--microprofile`; `--microprofile-visible` also requires that base flag. CLI prefixes are used as supplied, including paths relative to the launch directory. Outputs are `BASE.startup.json`/`.html` and `BASE.json`/`.html`. Runtime recording begins after the first presented scene frame. The timed stop is checked by the render loop, followed by a half-second asynchronous query-drain interval; slow frames or suspension can extend wall time and unavailable late samples stay explicit. No query-completion wait is added. An initialization failure or early exit can leave only the startup capture. A short runtime capture keeps servicing the startup export worker before saving its final report, and shutdown joins that worker; a startup export failure remains explicit. A standalone completed CLI capture exits; a combined benchmark/capture/legacy profile keeps its own completion condition.

`--microprofile` can be combined with `--capture`, the existing `--profile` or `--benchmark`. Standalone CLI recording keeps ordinary application controls and the recording indicator even with the profiler panel hidden. The existing `--profile`/`--capture` modes suppress ordinary widgets; combining them with `--microprofile-visible` draws only the profiler panel for a controlled visible-panel comparison. Screenshot readback and a visible viewer affect workload. A short trace has no automatic two-second warmup exclusion or sixty-second measurement qualification. Use the existing `--profile ... --profile-seconds 65` with matched camera/settings for throughput measurements, then compare recording disabled, hidden and visible in separate sequential runs. The measured checkpoint below reports one matched Linux cohort; it does not establish negligible overhead for other workloads or platforms.

## Diagnostic benchmark scoring

Any microprofiler recording during a benchmark tour makes that tour permanently **diagnostic and unscored**, even if recording stops before the tour completes. Frame statistics, CPU/GPU timing and workload counts remain available. Diagnostic reports retain result schema 2 and score version 3, add `run.diagnostic: true`, `run.scored: false` and a reason, and export Overall/CPU/GPU scores as JSON `null`; the UI/HTML display “Unscored”. A later clean run resets this diagnostic state. Unrecorded benchmark reports keep their existing schema and scoring behavior; cancellation still discards the incomplete result.

## Trace format and clocks

JSON uses `format: "heaven-microprofile"` and `schema: 1`, independently of benchmark-result schema/score versions. Each export includes `session_id`, `origin_ns`, retained `begin_ns`/`end_ns`, active state, metadata, loss counters, recorder memory accounting and these record arrays:

| Array | Main fields |
| --- | --- |
| `threads` | Stable trace thread ID and display name. |
| `spans` | Scope/parent/thread IDs, interval, name/category, context and `incomplete`. |
| `frames` | Render/loading kind, pending/accepted/rejected/cancelled outcome, interval, context and `incomplete`. |
| `counters` | Thread/time, name/category, numeric value and context. |
| `flows` | Cross-thread correlation ID, begin/step/end phase, thread/time, name and context. |
| `gpu_samples` | Pass/parent IDs, GPU interval, status/source/capability, context and submitted command/primitive/visible-renderable counts and draw-instance invocations. |

Context carries `capture_id`, `attempt_id`, `submission_id`, `filament_frame_id`, `renderer_id` and `view_id`; zero means absent. IDs and the absolute steady-clock origin are decimal strings to preserve 64-bit values in JavaScript. CPU times are nanoseconds relative to that steady-clock origin. GPU timestamps are nanoseconds relative to their own GPU frame, with no CPU calibration. Never align those axes, add CPU and GPU duration, or interpret a pass sum as whole-frame time. GPU intervals can overlap and command/primitive counts describe submitted work rather than unique scene geometry or hardware presentation. `draw_instance_invocations` sums instances over executed draws; it is not a count of unique visible placements. Older traces lacking this additive field have unavailable workload data, not an observed zero.

Exports also include a deterministic first-occurrence `strings` table and zero-based numeric `name_id`, `category_id` and `capability_id` references on records carrying those labels, including thread names. Inline labels remain present. Parsers accept older inline-only schema-1 traces and validate table references when supplied; these label indices are separate from decimal-string correlation IDs.

`stale_epoch_events` separately counts callbacks imported from an older capture. These ignored old-session events are informational, do not mean current events were lost and do not invalidate otherwise certified exclusive costs; dropped/overwritten current events remain loss. CPU submission correlation is conservative: snapshots retain a provisional submission ID only with accepted-frame or actual non-Dropped GPU proof for the same capture and attempt; explicit rejected/cancelled/pending frames override it. If the necessary acceptance history aged out, the submission ID is zero. Join on capture plus attempt rather than treating a nonzero provisional ID as acceptance.

GPU status is one of `Available`, `Pending`, `Unsupported`, `Disjoint`, `Error` or `Dropped`; source is `HardwareTimestamp`, `FenceEstimate` or `Unavailable`. The native Vulkan adapter checks the graphics queue's timestamp bits/period and query-pool creation. OpenGL checks timestamp-query entry points, counter bits, the disjoint extension and driver workarounds. Support is discovered at runtime, including on Android; platform/API names alone do not establish it. Unsupported or incomplete GPU work is not reported as a measured zero-duration pass. Existing whole-frame/fence timing remains distinct from dedicated pass timestamps.

Metadata records phase, application version/architecture, starting effective configuration/resolution, camera start/end, `application_overlay` mode, profiler-panel visibility and available CPU/platform/API/GPU/driver/capability details. Profiler visibility is latched at each capture start; changing it while recording preserves the initial `overlay_visible`, records `overlay_visible_final` and marks the capture mixed. A live settings or resolution change marks `settings_mixed: "true"` and records the final configuration/resolution; the analyzer refuses to compare a mixed-settings capture. Metadata does not by itself prove exact binary, source or asset identity. Retain executable/source/asset hashes, commands, terminal status and effective settings with any comparison receipt.

## Export and offline analysis

The HTML contains its data and viewer, requires no network service, and provides CPU task navigation, counters, accepted complete CPU-frame intervals, per-scope distributions and a separate GPU-frame selector. JSON retains the structured records for independent tooling. The writer owns an immutable snapshot on a worker thread, reports queued/writing/complete/error state and accepts one export at a time. Writer instrumentation belongs to an active capture at dispatch; an immutable export cannot contain its own future serialization/I/O, though a later snapshot of that ongoing capture can. Each destination file is replaced atomically; the JSON/HTML pair is not one filesystem transaction. Reusing an explicit prefix replaces an earlier export where the filesystem permits; automatic UI prefixes avoid routine collisions.

```bash
python3 scripts/analyze_microprofile.py build/traces/ledge.json \
  --output build/traces/ledge-summary.json
python3 scripts/analyze_microprofile.py build/traces/repeat-a.json \
  --compare build/traces/repeat-b.json \
  --output build/traces/repeat-comparison.json
```

The analyzer validates the schema, clock contract, intervals, enum values, label references and decimal IDs. CPU inclusive durations overlap by design. Exclusive duration subtracts the union of direct children on the same thread, so overlapping children are not double-subtracted and another thread's work is not subtracted. Incomplete spans are counted separately. Dropped/overwritten events or incomplete/out-of-parent children make exclusive cost unavailable rather than guessed. Time distributions use linearly interpolated ordered quantiles (R7) in nanoseconds. Counter summaries retain sample count, first/last values and distributions in the counter's own units; GPU workload summaries retain submitted command/primitive/visible-renderable counts and draw-instance invocations. GPU timing aggregates separate sources and omit unavailable samples; frame statistics exclude incomplete accepted intervals. Analysis lists the longest retained complete accepted CPU frame intervals (`worst_frames`) and per-thread observed span unions/wall coverage (`thread_activity`); these are neither CPU utilization nor full activity/FPS, and loss/partial history is flagged. These are diagnostic observations, not benchmark scores or measured display latency.

`--compare` requires identical full metadata with known, nonempty `cpu`, `gpu`, `driver`, `driver_version`, `api`, `resolution` and `effective_settings` values; missing, empty or unknown/unavailable placeholders are rejected with named fields. Older or incomplete traces remain individually analyzable. It compares matching named/category scopes across trace-local thread identities. It omits uncertified exclusive costs and retains each side's scope counts, counters, GPU workloads and loss information. Equal metadata is a guard, not proof of equivalent hardware, input or workload; settings/overlay changes deliberately fail that comparison guard. The current CPU description includes observed MHz, so this strict guard can conservatively reject captures from the same CPU with a different recorded frequency; inspect the disclosed identity mismatch instead of treating it as a performance result. Retain each single-trace summary and separate throughput evidence before ranking costs.

## Bounds and validation limits

Recorder storage is allocated on first activation: the default budget is 64 MiB on desktop and 16 MiB on Android, with 64 thread-registration slots and a quarter of event storage reserved for GPU records. Metadata and labels are bounded; long labels are truncated and counted. Thread event callbacks use preallocated rings and a nonblocking lock attempt; contention drops events explicitly, and full rings overwrite old events explicitly. The requested history is an upper retention window, not a guarantee that all events fit. Snapshots, UI hierarchy caches, writer copies/serialization and GPU query objects use additional memory outside the recorder-ring budget.

The GPU adapter bounds in-flight storage to 16 frames and 256 passes per frame, does not wait for query completion and does not reuse an in-flight interval. Saturation or query failure is reported rather than silently synchronized. The in-app viewer clips task rows, caps task primitives in a dense view and tells the reviewer to zoom/filter; export keeps the retained snapshot. Instrumentation covers named project/Filament scopes, not every instruction or all external driver/kernel work. CPU wall intervals include waits and scheduling; they are not CPU utilization. A stopped recorder avoids event collection, but no zero-overhead claim is made. The live CPU canvas also bounds its ImGui vertex count below Filagui's 16-bit index limit; dense views request zoom/filter rather than wrapping indices. This live drawing limit does not remove retained events from an export.

Focused host checks cover CLI bounds/persistence isolation, immutable freeze/save intents, GPU frame selection and CPU-attempt identity links, unavailable GPU rows, compact viewport layout/focus/dense drawing limits, sticky diagnostic scoring and independent interval-union/loss controls. The final canonical CTest run passes seven host suites and separately skips the opt-in GPU harness; the Python analyzer has ten independent tests. Final native Vulkan/Wayland and OpenGL/X11 suites each pass 46 checks with four documented skips, including active profiler resize/reload and window lifecycle. Earlier fixed-camera recording-on/off image comparisons include off repeats: roughly 0.467/255 mean absolute channel variation also appears in repeats, so these images do not establish byte-exact parity. The final desktop raster independently verifies readable graphs and removal of the dense index-wrap corruption. The exact final executable also captures the authored AO-on airship at 1280×720 on both APIs after 45 warmup frames: both Vulkan recording-on/off and off-repeat pairs are byte-identical. OpenGL recording-on/off differs by at most two RGB8 levels (roughly 0.466/255 mean channel difference), while its off-repeat pairs in this cohort are byte-identical. Earlier matched repeats exhibit similar two-level variation, but this final OpenGL cohort does not establish byte-exact parity or independently isolate that variation. Both final recording-on images are visually inspected. This is a fixed real-mesh control, not a complete scene matrix; receipt: `build/microprofiler/20261009/selection-final-authored-parity/verification.json`.
