## CR-01: enforce the requested rendering device

[The launcher](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/scripts/run.sh#L336) sets `MESA_VK_DEVICE_SELECT` and PCI-form `DRI_PRIME`, then announces that GPU. These settings leave other devices enumerable. Filament's physical-device selector (`lib/filament/filament/backend/src/vulkan/platform/VulkanPlatform.cpp:481` in the populated dependency checkout) subsequently sorts devices by its own preference and device type. The application supplies no explicit Vulkan GPU preference, so a discrete device can override the requested integrated device. The vendored source is reconstructed through [the pinned patch workflow](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/patches/filament/README.md) rather than tracked as ordinary repository files.

The native Linux control explicitly requests AMD `1002:164e` at PCI `0000:09:00.0`. The launcher prints that AMD selection, but the backend selects Intel `8086:e223` from three devices. Adding only `MESA_VK_DEVICE_SELECT_FORCE_DEFAULT_DEVICE=1` makes the same request select the AMD device from one enumerated device; both runs exit zero. This proves a selection defect rather than an unusable requested device. The backend's actual GPU information remains available, but the wrapper's selection promise is false and a benchmark can measure unintended hardware.

Proposed correction: enforce explicit selection through device isolation on the supported Mesa path or a native device identity passed to the Vulkan platform, and check requested versus actual identity. Keep the default policy separate and preserve both Vulkan and OpenGL launch behavior. A regression must include a usable integrated GPU alongside a discrete GPU; merely checking exported environment strings cannot detect this failure. The force-default environment variable is a verified control on this Mesa host, not a universal cross-driver fix.

Evidence: `build/code-review/20261104/renderer/gpu-selection-receipt.json`, `gpu-explicit-amd.log` and `gpu-explicit-amd-force.log`. The receipt retains exact argv/environment, actual device logs, source hashes and runtime binary identity. ## CR-02: distinguish source surfaces in cache identity

[The cache key](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/tessellation_cache_archive.cpp#L265) hashes the mesh path and whole-file fingerprint, surface name, kind and tessellation parameters. It includes neither a source-surface ordinal nor that surface's original vertex/index identity. Distinct surfaces in one mesh therefore collide when their names and parameters match. [Scene loading](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/scene_rhi.cpp#L1533) loads directly into the current surface; [staged reads](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/tessellation_cache_archive.cpp#L293) can return the previous surface before the first archive has even been published. Duplicate names are already supported by [the staged-scene fixture](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/tests/unit_staged_scene_load.cpp#L103).

A freshly compiled harness writes and parses a valid synthetic two-surface mi08 source, stages its triangle at x=0, and loads the different same-name triangle whose first vertex should be x=100. The cold load reports a hit and returns x=0; reopening the archive reproduces the same replacement. This is silent geometry substitution, not an ordinary cache miss. The harness exercises actual mesh parsing and the cache API; it is not an end-to-end scene capture. A scan of 63 currently extracted static Heaven mi08 files found no duplicate names, so a stock-scene manifestation is not established.

Proposed correction: carry a stable source-surface identity into static and skinned cache keys and metadata, invalidate ambiguous old entries, and handle legacy import conservatively. Add cold/staged and warm regressions containing distinct same-name surfaces with equal counts and parameters; counts alone cannot identify the surface. Preserve the existing material-name mapping independently of cache identity.

Evidence: `build/code-review/20261104/cpu-assets/cache_collision.cpp`, `reproduce_cache.py`, `cache-reproduction.txt` and `receipt.json`. Re-run the retained actual-source harness with `python3 build/code-review/20261104/cpu-assets/reproduce_cache.py`.

## CR-03: validate ZIP EOF before accepting cached geometry

[The tessellation entry reader](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/tessellation_cache_archive.cpp#L181) reads exactly the advertised byte count and checks `zip_fclose`, but never reads through logical EOF. Libzip can defer CRC verification until the next read. [The ordinary ZIP asset stream](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/asset_file_system.cpp#L365) already handles this with an explicit one-byte EOF probe; the cache's independent reader omits that protection.

The reproducer changes the first cached vertex from x=0 to x=50 while retaining the original ZIP CRC. Both STORE and normal DEFLATE entries are accepted as hits and return x=50; `validate_zip_archive(..., true)` independently rejects both archives. Binary sizes and indices remain valid, so the cache decoder's structural checks cannot detect the altered geometry. An accidentally damaged cache can therefore affect rendering instead of being rejected and regenerated. This is an integrity defect; the check does not establish arbitrary code execution.

Proposed correction: require successful logical EOF and CRC validation before decoding or committing the entry, retaining close/error handling. Test both compression modes with a shape-valid corrupted payload and require a cache miss without mutating the destination. Preserve correct-cache hits and ordinary scene loading.

Evidence: the same `cpu-assets/reproduce_cache.py` and `receipt.json` retain the corruption construction, both accepted payloads, independent validation failures, compile command and actual-source hashes.

## CR-05: buffer small sequential reads from ZIP assets

[The mesh loader](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/mesh.cpp#L176) reads position and packed normal arrays separately for every vertex, followed by small UV/index reads. [AssetBinaryReader](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/loader_validation.h#L56) forwards each request to its stream; [the ZIP stream](https://github.com/dev-zetta/HeavenBench/blob/2288b965cd7d6edd7b1ea48023463063c5998882/benchmark/src/engine/asset_file_system.cpp#L280) locks the archive and enters libzip for each read. This creates avoidable per-field overhead on compressed mesh inputs.

A scratch 64 KiB per-reader read-ahead prototype was compared with the unmodified reader using actual `load_mi08` on the original `fort.mesh` in a one-entry DEFLATE asset pack. Both executables freshly compile the same mesh loader and asset filesystem; only a copied `loader_validation.h` differs. Each trial includes open/seek/decompression, allocation, decoding, tangent generation and destruction, excludes two seconds of warmup, and measures at least 60 seconds. Retained task build/test/render logs finish before the original trial's approximately 12:34:25–12:35:27 CET window and the prototype's subsequent window ending at 12:36:29. Other desktop activity and CPU affinity were not recorded, and the trial order was not reversed; repeat under tighter controls before generalizing the timing difference.

| Reader | Completed measured loads | Measured seconds | Mean time per load |
| --- | --- | --- | --- |
| Original | 2,458 | 60.006625 | 24.412785 ms |
| 64 KiB read-ahead prototype | 5,766 | 60.001145 | 10.406026 ms |

Both controls produce 77,408 vertices and 307,839 indices with identical vertex/tangent/index hash `aac0eace20318646`. The prototype takes 57.4% less time per load in this one CPU microbenchmark on AMD Ryzen 9 7945HX3D/Clang 21.1.8. This demonstrates a useful loader optimization opportunity; it does not establish complete-scene startup savings, rendering FPS, visual acceptance or a safe production implementation. The scratch buffer costs 64 KiB per reader plus possible bounded transient moves/copies. The prototype is retained only under ignored build evidence.

Proposed correction: add bounded sequential read-ahead without weakening short-read, seek/tell, EOF/CRC or malformed-input behavior. Test directory, memory and ZIP streams, forward/backward seeks, truncated/corrupt inputs and multiple readers, then measure a full cold/warm scene load. Keep memory bounded rather than buffering every complete asset by default.

Evidence: `build/code-review/20261104/cpu-assets/loader-receipt.json`, `loader_long.cpp`, `buffered-prototype/engine/loader_validation.h`, and `loader-long-original.txt`/`loader-long-buffered.txt`. The receipt retains source/asset hashes, exact compile/run commands, machine/compiler identity and measurement limits. These are one serial trial per variant, without a repeated whole-scene acceptance claim.
