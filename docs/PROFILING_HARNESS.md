# Fixed-camera performance comparisons

`scripts/profile.sh` continues to run scored full tours and feature ablations. The separate Linux `scripts/profile_compare.py` harness compares two exact renderer binaries at one fixed camera without recording a score, screenshots, microprofiles or shader diagnostics. It uses the existing renderer and launcher; it changes no driver, clock, power or security setting.

Prepare an experiment with `python3 -E -B scripts/profile_compare.py prepare --spec SPEC.json --cohort build/profiles/UNIQUE`, then invoke `run --cohort ... --label LABEL` once per declared label. Use `analyze --cohort ...` after all windows, or `audit --cohort ... --entry windows/LABEL` to verify an individual closure. A specification binds the exact binaries and their SHA-256 hashes, input configuration, assets, geometry seeds, PCI GPU, Vulkan driver, expected effective profile metadata and runtime geometry, camera, run order, durations, repeatability threshold and native run/wall-time limits. Retain the sealed `protocol` entry with each report as the reproducible specification. Different hardware or workload signatures cannot be pooled.

The default prospective order is two shader-cache priming captures (A then B), two baseline pilot captures, and two complete ABBA quartets. Priming defaults to 65 runtime seconds; a prospective integer `prime_seconds` can extend both priming runs up to `profile_seconds` for longer cache and thermal preconditioning. Priming combines both binaries' Mesa caches into one sealed seed; every measured window gets an independent writable copy of that exact seed and the same warm geometry caches. The pilots must pass the declared baseline range limit before comparison begins. Request at least warmup + measurement + two seconds of runtime. Analysis uses the shortest final whole-interval suffix reaching the declared measurement duration after at least the declared excluded prefix. Durations belong to the sealed experiment and cannot be changed retrospectively. Native statistics after the renderer's original two-second warmup remain separately available. No interval is trimmed, interpolated or removed as an outlier. Shader-cache changes are disclosed.

An optional `shader_seed_directory` and `shader_seed_provenance` can reuse a completed combined cache artifact without new native priming. The provenance descriptor requires the source `cohort`, entry `combined-shader-seed`, exact typed `ref`, and sorted `inventory` of member names, sizes and SHA-256 hashes. Preparation recursively verifies the successful, owned and drained native producer and matches both binaries, assets, hardware/driver, settings, camera and geometry against the new experiment. It then imports only the cache bytes into a new typed file tree. This mode omits `prime_seconds` and declares exactly ten new launches: two pilots and eight comparisons. It creates no synthetic priming windows and imports no previous timing eligibility. Every attempt and result labels this artifact-only policy; the external source store must remain available for reproducing its qualification.

Each cohort has a fresh UUID. Each window is attempted once; an immutable attempt entry is published before launch. Existing attempts, windows, reports and named entries are never replaced, including failed or interrupted attempts. A failed cohort needs a new directory, not a retry under the same label. Mutable work logs are sealed only after the owned native process and descendants drain. A dedicated Linux subreaper, identity-checked pidfd signalling, bounded logs and timeout cleanup retain cancellation and failure evidence without signalling unrelated processes. The supervisor uses a private session and a parent-death guard to drain after controller loss; the direct workload receives a kernel SIGKILL if its supervisor dies. Parent identity checks close startup races. An unrecoverable supervisor death does not prove arbitrary descendants were drained or produce a valid native completion receipt, so such captures remain unavailable for timing acceptance. Real CPU tests cover abrupt controller/supervisor loss, pre-arm races, descendant escape, cancellation, concurrent publication, corruption and missing nested proofs.

The store contains content-addressed blobs and typed JSON records with explicit reference edges. Reports recursively verify every referenced object, length, type and digest before analysis; putting an arbitrary path or digest inside a payload does not create a verified edge. The default evidence limits are 128 MiB per object and 512 MiB per closure; this harness explicitly allows 512 MiB objects and 2 GiB closures to embed geometry caches. Large asset ZIPs are retained externally and checked by SHA-256 before and after native work, rather than copied into each report. Preserve those original inputs for reproduction. The store uses POSIX directory descriptors, no-follow file opens and exclusive atomic publication and fails on unsupported hosts.

The controller records the actual executable and mapped Intel driver inodes, effective settings, full-scene geometry, native process completion, readable competing processes, labelled GPU temperature/frequency sensors and the kernel interval. Sparse observations do not prove frame-level clocks, power or exclusive desktop GPU use; absent telemetry stays unavailable. No CPU/GPU clock alignment or per-pass attribution is inferred from the ordinary profile's asynchronous last-completed GPU samples.

Acceptance requires all eight comparison windows, identical hardware/workload signatures, the declared baseline range cap, positive improvement in each quartet, and a pooled mean improvement exceeding baseline range, candidate range and first-to-last baseline drift. A completed first quartet with non-positive gain can be rejected immediately because no later quartet can satisfy that necessary condition; retain a rejection report with the completed scope and do not claim eight-window acceptance. Partial or failed cohorts remain evidence and cannot qualify a winner. Visual correctness is an independent gate: reuse only a documented exact-binary quality qualification or run matched native visual fixtures before accepting a candidate.

## Optional application monitoring contract

A specification may declare `hardware_monitoring` to make the application's read-only monitoring policy part of workload identity. It must contain exactly eight stable fields: `mode`, `clock`, `power_limit_w`, `device_vram_total_mb`, `gpu_high_c`, `gpu_critical_c`, `vram_high_c` and `vram_critical_c`. Mode and clock must be nonempty strings; the six metrics must be finite nonnegative numbers or `null`, with booleans rejected as numbers. The actual profile's `hardware_telemetry` must contain exactly those eight fields plus the thirteen observations below, and its stable fields must equal the sealed contract. A changed sampling mode, clock description, power limit, VRAM capacity or temperature limit cannot silently become an optimization gain.

The thirteen dynamic observations are `sample_monotonic_ns`, `available`, `reason`, `gpu_temperature_c`, `vram_temperature_c`, `power_w`, `graphics_clock_mhz`, `memory_clock_mhz`, `fan_rpm`, `utilization_percent`, `memory_utilization_percent`, `device_vram_used_mb` and `throttle_reason`. Their values may vary between windows and are retained separately from the comparison signature. Timestamps must be unsigned 64-bit integers, availability must be boolean, reason must be a string, throttle reason must be a string or `null`, and other readings must be finite nonnegative numbers or `null`. Missing or extra fields, invalid types, nonfinite/negative readings, a mismatched stable contract or a result missing its declared observations fail closed. Valid unavailable readings remain unavailable; they are not zero or proof of unthrottled operation.

Analysis verifies the declared contract and observations in every window, then exports `hardware_monitoring.contract` and `observations_by_window`. These are latest host observations, not frame-aligned measurements; full histories remain in each original profile's `hardware_telemetry_samples`. They do not align CPU/GPU clocks, attribute GPU-pass costs or establish power/clock causality. Omitting `hardware_monitoring` preserves the legacy protocol/signature behavior and does not force an external observer. The controller's 37 CPU tests cover contract/type validation, preserved legacy behavior, observation disclosure and missing/foreign analysis evidence; CPU tests alone are not a native performance or overhead qualification.

## Optional Intel observer state

On the November 17 Intel host, read-only `xpu-smi` polling changed measured baseline time by about 2.9% in a prospective Off/On/On/Off control. Treat observation as part of the workload identity; never compare polling-on results with polling-off results as an optimization gain. This does not fully explain the earlier 380-ms phase. See [the performance history](PERFORMANCE_OPTIMIZATIONS.md) for exact captures and limitations.

A Linux protocol can explicitly declare `power_observer` with `path` and the complete `profile_harness.monitor.file_identity(path)` dictionary under `identity`. The optional controller invokes `python3 scripts/profile_power_window.py COHORT LABEL` instead of the ordinary run command. It uses only fixed read-only power/clock/memory queries for the protocol's PCI device, verifies the executable before and after, bounds the child, stops it after native completion and seals `power_observers/LABEL` linked to the native window. Missing coverage or qualification prevents acceptance. The observer never enables EU sampling or sets clocks/power limits. It remains off by default; standard application runs and scores are untouched.

The reusable wrapper follows the archived native prototype, with stricter coverage validation exercised against its captured CSV files. Its integration is CPU-tested; do not describe that as another native performance or cross-platform acceptance run.

The completed November 17 full-Heaven Intel cohort used a declared application sysfs worker at up to 1 Hz, the controller's existing two-second read-only observations (0.5 Hz), and external `xpu-smi` polling off. It used Intel 8086:e223, Mesa 26.0.8-1ubuntu0.3, Vulkan/X11, 1920×1080, four-sample MSAA and unchanged High contact shadows at the fixed village camera. Twelve fresh windows comprised A/B shader priming, two baseline pilots and both ABBA quartets. Each requested 260 runtime seconds, with at least 75 excluded seconds and a final whole-interval suffix of at least 180 seconds; no imported timing or retry window qualified the result.

All eight comparison windows passed the sealed gates: baseline range was 0.077074%, candidate range 0.029231% and first-to-last baseline drift 0.031254%, below the declared 1% baseline cap. Both quartets improved (3.700908% and 3.702367%), and the pooled mean fell from 316.768278556046 ms to 305.04264728880713 ms, a 3.701643% reduction exceeding all three noise measures. The recursively verified analysis is retained under `build/intel-register-pressure/20261117-monitored-optimization/benchmark/analysis-readback-01.json` for cohort `ae940f8e-7683-4cef-86e0-ca8d009033c3`. This qualifies that exact cohort and observer condition; it does not measure monitoring overhead, establish a whole-tour score or extend acceptance to other hardware/settings.

That study additionally used ignored, task-specific wrappers for its total native/wall-time budget and one-shot durable controller transport. Those controls and their receipts remain with the study; they are not new public-harness defaults or a general native overhead claim. The reusable external power observer remains opt-in and off by default.
